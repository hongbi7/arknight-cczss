# 业务流程与回归测试

本文记录当前三种协议的用户流程、关键状态和自动化覆盖范围。前端使用同一个页面容器切换状态；原始模式的局面由加密 token 驱动，异类审查每次成功请求后也必须替换 token。

## 一、协议选择

页面初始化时读取公开干员名称和立绘映射，清空终局校验的战术指令轮换历史，然后进入协议选择页。

1. **终局校验**：配置 1–20 次猜测机会，进入限次识别。
2. **全域检索**：不限制猜测次数，随时可以主动揭晓。
3. **异类审查**：先选择综合或六个单域主题，再开始十轮审查。

刷新页面会重新初始化并清空战术指令历史。切换模式后再次进入终局校验会以新轮换开始；「再来一局」以及未修改次数时的「应用本局」保留轮换历史；修改次数后应用会清空历史。

## 二、终局校验

```text
选择协议
  → 创建局面和战术指令
  → 猜测干员
      ├─ 命中谜底 → 终局档案 → 成功结算
      ├─ 尚有次数 → 新档案置顶 → 继续猜测
      └─ 次数耗尽 → 四选一终局抉择
                         ├─ 选对 → 终局档案 → 成功结算
                         └─ 选错 → 先装载错项普通档案
                                  → 再装载谜底终局档案 → 失败结算
```

每次猜测都会比较职业、分支、星级、部署位、标签、性别、出身地、种族、势力、技能范围、费用和本轮轮换维度。满足战术指令会推进解码；达到目标后可解锁情报。剪影类情报在终局档案完全加载并聚焦后，才以同类扫描动效把战术指令区域的剪影或局部显影替换为该干员对应的剪影立绘。

战术指令以技能、战斗、身份、后勤、形象五个大类轮换并参考本页面会话内历史降低大类重复。珊瑚海岸参与同一套刷新生命周期，但有独立偏置：首局约 30%，前三局尚未出现时提高机会；前三局出现一次后恢复常规权重，连续出现受到抑制，累计出现三次后降低权重。首轮五族后，形象档案获得小幅权重提升。

主动点击「揭晓答案」必须先经过确认弹窗；取消返回当前局，确认后直接装载谜底终局档案并按失败结算。

## 三、全域检索

```text
选择协议
  → 创建无限局面
  → 任意次数猜测
      ├─ 命中谜底 → 终局档案 → 成功结算
      └─ 未命中 → 新档案置顶 → 继续猜测
  → 可随时主动揭晓 → 确认 → 终局档案 → 失败结算
```

移动端在第一次猜测后进入档案工作区：左右滑动在立绘与档案数据间切换，上下滑动在多份档案间切换；终局档案的内部内容滚到顶或底后，同一次纵向手势会接力滚动外层档案列表。底部保留继续输入和揭晓入口。

移动端档案不会把三个技能范围硬塞进单个维度格：格内保留各技能的重叠数摘要，点击「展开完整技能范围」后在绑定 `visualViewport` 的底部详情层中显示全部技能、范围网格、吻合状态和技能机制。终局校验解锁的情报奖励也使用同一详情层自动展示，并可从战术指令条的「查看情报」重新打开；奖励卡不再插入档案列表，因此不会压缩档案可读高度。剪影与局部显影的放大预览层级高于移动详情层，同样绑定当前 `visualViewport`，关闭按钮始终保留在可视区。桌面端继续使用原有完整范围网格、左侧战术情报面板和立绘预览布局。

## 四、异类审查

```text
选择异类审查
  → 选择综合或单域主题
  → 十轮循环：装载四张候选档案
      → 可选：综合主题使用共性扫描器
      → 标记一名异类
      → 二次点击“确认异类”提交
      → 展示正确异类、共性规则、证据、得分和难度变化
      → 下一份档案
  → 第十轮后展示总分、准确率、评级、难度和各域统计
  → 重新审查或返回协议选择
```

综合审查初始有两次扫描，每题至多使用一次，每连续答对三次奖励一次；单域主题不支持扫描。难度从标准开始，三连对升级、两连错降级。提交后的复盘阶段才能公开异类、规则和证据。

## 五、自动化分层

- `npm test`：游戏与异类审查服务端规则、token 和计分单元测试。
- `npm run test:e2e:desktop`：1440×1000 Chromium，覆盖三种协议的主要业务链路。
- `npm run test:e2e:mobile`：360×760 触屏 Chromium，复用主要业务链路，并验证横向翻页、纵向档案滑动和移动布局。
- `npm run test:e2e`：依次运行桌面与移动项目。失败时保留截图和 trace 到 `output/playwright/`。
- `npm run test:e2e:device`：通过无线 ADB 连接真实 Android Chrome，检查软键盘、浏览器工具栏和视觉视口相关问题。

首次执行浏览器自动化前运行：

```powershell
npx playwright install chromium
npm run test:e2e
```

真机执行示例：

```powershell
$env:ADB_PATH = "C:\path\to\adb.exe"
$env:ADB_SERIAL = "192.168.1.30:37123"
$env:MOBILE_TEST_URL = "http://192.168.1.20:3300/"
npm run test:e2e:device
```

真机脚本默认把不合理布局记录为发现但返回成功，便于先收集报告；设置 `$env:MOBILE_STRICT = "1"` 后，任何发现都会令命令失败。报告和截图位于 `output/playwright/device/`。

## 六、当前已知移动端问题

1. **高（条件触发）**：在部分地址栏/滚动状态下，软键盘弹出后提交按钮会被键盘遮挡，只剩输入法动作键可提交。
2. **中**：终局校验移动首屏被标题、战术指令和次数控制占满，猜测输入位于首屏以下。
3. **中**：异类审查题头和主题范围占用过高，题目装载后四张候选卡都不在首屏内。
4. **中**：异类主题页顶部说明较高，主题详情与开始按钮需要较长距离滚动；详情列表本身还会先消费一次纵向滑动，再链式滚动页面。

上述第 2、3 项已用 Playwright `test.fail` 作为预期失败锁定；第 1 项依赖真实 Android 的软键盘、地址栏与视觉视口行为，由无线 ADB 真机脚本检测。共性扫描结果、立绘预览可视视口、揭晓确认弹窗宽度、外层横向溢出和终局档案边缘滚动接力均已有通过中的移动端自动化断言。
