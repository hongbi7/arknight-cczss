# 2 核 / 2 GiB / 3 Mbps 测试环境与容量摸底

建议先搭一台本地 Ubuntu 虚拟机，复现生产服务、内存限制和共享出口带宽；再用相同实例规格的测试 ECS 校准容量。压测程序运行在虚拟机外。当前仓库已有功能测试和部署检查；本文是测试环境与压测实施方案，尚未安装虚拟机、加入 k6 脚本或生成容量测试结果。

## 环境结构

```text
Windows 宿主机：k6（协议压测） + Playwright（少量浏览器验收）
       │
       │ 隔离的虚拟网络，访问虚拟机私网 IP
       ▼
Ubuntu 虚拟机：2 vCPU、固定 2048 MiB 内存
       │  测试网卡共享出口限制 3 Mbps
       ▼
Nginx：静态资源 + /api/ 代理
       ▼
Node.js 24：127.0.0.1:3000，由 systemd 守护
```

Windows Pro / Enterprise 可以使用 Hyper-V；选择前先确认系统版本与硬件虚拟化支持，安装通常涉及管理员权限及重启，参见 [Microsoft 安装说明](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/install-hyper-v)。已有可用的 Ubuntu 虚拟机工具也可以继续使用。测试重点是复现完整 Ubuntu、Nginx 和 systemd 环境，不需要改变生产部署架构。

| 项目 | 本地设置 | 校准方式 |
| --- | --- | --- |
| CPU | 2 个虚拟处理器，保留生产的单 Node 进程 | 记录 ECS 实例规格、CPU 型号；本地 2 vCPU 不等于云端同等算力 |
| 内存 | 固定 2048 MiB，关闭动态内存 | 内存供整个 Ubuntu 使用，包含 Nginx、Node、部署器和系统缓存 |
| 服务限制 | 沿用 Node 服务和部署服务各自的 `MemoryMax=768M` | 两个上限独立，部署时还需要观察总内存与 Swap |
| Swap | 与实际 ECS 保持一致 | 有无 Swap 会改变 OOM 和长尾延迟，不能只对齐物理内存 |
| Ubuntu | 与 ECS 相同版本，尽量匹配软件版本 | 先在 ECS 记录 `/etc/os-release`、`node -v`、`nginx -v` |
| 磁盘 | 仓库和 releases 放在虚拟机 Linux 文件系统 | 不用 Windows 共享目录承载运行目录；本地 SSD 仍不能等同云盘 |
| 网络 | 所有访客共享 3 Mbps 虚拟机出口 | 另测不限制出口的 API 基线；延迟和丢包单独设置、记录 |
| 配置 | 同样的 Nginx 缓存规则、systemd unit、发布目录结构 | 使用独立测试密钥，不复制生产密钥 |

宿主机还要有足够空闲 CPU 和内存运行 Windows、压测器及浏览器。测试时避免其他重负载任务，并记录宿主机是否也达到资源上限。虚拟机 CPU 型号、宿主调度、磁盘、公网线路都与 ECS 有差异，因此本地结果主要用于比较版本、发现瓶颈，不能直接承诺生产可承载的在线人数。

## 网络与未绑定域名的访问方式

为虚拟机设置隔离测试网卡，通过私网 IP 访问 Nginx，无需域名或证书。仅在测试虚拟机中，为 Nginx 增加该私网 IP 的监听；保留 `127.0.0.1:80` 供部署器本机校验，Node 仍只监听 `127.0.0.1:3000`。测试 Nginx 的静态根目录仍指向 `app/public`。生产模板继续保持当前的本机监听配置。

在 Ubuntu 的隔离测试网卡上用 Linux `tc` 的 TBF 队列限制总出口为 `3mbit`。限速必须作用于所有客户端的共享出口；给每个浏览器单独设置 3 Mbps 会把总带宽放大。只操作测试虚拟机的测试网卡，并先记录已有队列配置。

TBF 的 `latency` 参数表示排队时间上限，并不是公网往返延迟；需要模拟延迟时另用 `netem`，清楚记录施加的方向与最终测得的 RTT。参见 [Ubuntu TBF 手册](https://manpages.ubuntu.com/manpages/noble/en/man8/tc-tbf.8.html)。第一轮可以只限制带宽，再补充不同 RTT 的对照组，避免同时改变多个条件后无法定位瓶颈。

阿里云固定公网带宽主要对应实例的出网能力，不能据此把 GitHub 下载到 ECS 的速度也假定为 3 Mbps，参见 [阿里云公网带宽说明](https://help.aliyun.com/zh/ecs/public-bandwidth/)。

服务容量测试与真实公网体验需要分别报告：本地私网 HTTP 能测服务和共享限速；最终 HTTPS、地域延迟和公网波动，需要具备对应条件的测试环境再验证。

## 自动化分为三层

| 层级 | 运行地点与触发方式 | 验证目标 |
| --- | --- | --- |
| 功能回归 | 已有 GitHub `Production CI`，随 PR / main 提交运行 | 游戏逻辑、数据完整性、桌面 / 移动端核心流程、部署故障逻辑 |
| 部署集成 | Ubuntu 测试虚拟机，选定通过 CI 的提交后运行 | 真实 systemd / Nginx、目录迁移、候选预检、切换、重启、回滚 |
| 性能摸底 | 虚拟机外的 k6 + 少量浏览器，手动触发为先 | 容量、带宽、延迟、稳定性、带流量部署的资源峰值 |

已有可复用入口：

- `npm test`：游戏逻辑测试。
- `npm run validate:production`：提交的数据及素材完整性。
- `npm run test:deployment`：健康端点和部署器故障场景。
- `npm run test:e2e`：浏览器功能回归，当前配置管理自己的本地服务。
- `node scripts/check_deployment.js --base-url http://<测试虚拟机IP>`：对已运行的 Nginx 入口执行健康及三种模式开局检查。

现有 E2E 有测试数据和本地服务依赖，不能仅把地址改成虚拟机 IP 就认为完成了远程验收。远程浏览器冒烟应另建配置，通过公开 API 完成流程。大量 Playwright 浏览器也不适合作为首选吞吐压测器。

自动化落地顺序：

1. 建好虚拟机、服务和基线快照，人工验证一次发布与回滚。
2. 在虚拟机外加入 k6 场景，先跑通单用户完整流程，再增加负载。
3. 固定代码提交、题库版本、环境配置和场景参数，产出首份基线报告。
4. 加入手动触发的自动化入口：部署指定版本到测试机 → 冒烟 → 压测 → 保存汇总指标。
5. 结果稳定后，再选择少量短测作为性能回归检查；较长的压力与耐久测试单独运行。

如果以后使用 self-hosted runner，它应运行在测试控制机，并只执行受信任的任务；生产 ECS 不承担 GitHub 作业或压测客户端。GitHub 托管 runner 的共享硬件与网络波动适合功能回归，不适合直接得出这台 ECS 的容量数字。

完整接入前，性能测试不会阻止现有发布。若以后要让它成为发布条件，需要显式把必需的性能检查加入 `Production CI` 的成功条件，单独创建另一个 workflow 并不会自动成为当前部署器的门禁。

本方案不改变生产每天北京时间 12:30 的部署检查，也不在生产机安排满负载测试。

## 必测的负载场景

| 场景 | 请求与缓存模型 | 目的 |
| --- | --- | --- |
| API 基线 | 经过 Nginx，仅 API，不限制测试网卡出口 | 观察 Node CPU、加解密和 JSON 处理能力 |
| 首次访问 | 新访客缓存为空，加载页面、脚本、样式及浏览器实际请求的图片并开始游戏 | 观察 3 Mbps 出口下的加载与交互体验 |
| 已有缓存的游玩 | 已获取且仍有效的静态资源不重复下载；遇到新图片仍请求；API 每次请求 | 模拟回访用户，不能把所有游玩都简化为 API-only |
| 模式混合 | 分别覆盖 sudden、endless、anomaly，再按明确比例混合 | 防止某一种轻量 API 掩盖整体成本 |
| 带流量部署 | 中等稳定负载下执行候选启动、切换、重启与回滚 | 观察 2 GiB 内存峰值、短暂失败和旧 token 能否延续 |

冷缓存指浏览器或协议压测器的资源缓存为空，不代表清空 Linux 页缓存。两者影响不同，应分别标注。k6 协议请求不会自动运行页面 JS、加载所有图片或复现浏览器缓存，需要显式建模；用少量浏览器记录真实页面请求，校准协议场景的资源清单、并行请求与缓存行为。参见 [k6 网站负载测试说明](https://grafana.com/docs/k6/latest/testing-guides/load-testing-websites/)。

资源清单不能只按页面可见性筛选：当前 HTML 中未设置懒加载的图片，即使被 CSS 隐藏也可能发起请求；还要包含当前模式的 CSS 背景与交互后动态插入的图片。以浏览器网络记录为准，并保留动态卡片和候选弹窗实际的懒加载行为。

本项目每局必须串行使用新 token：

- `sudden`：`new?v=3` → 多次不同合法名字的 `guess` → 未提前结束且机会耗尽时 `choices` → `pick`，另覆盖揭晓分支。猜中后应按响应结束当前局。
- `endless`：`new?v=3` → 多次 `guess` → 正常结束或 `reveal`。
- `anomaly`：`themes` → `new` → 每题 `answer`，若还有下一题再 `next`；完整十题通常是十次 answer、九次 next。混合域按返回的可用次数插入 scan，单域不使用 scan。

每个虚拟用户独立保存会话，按成功响应更新 token 和当前选项，模拟思考时间。压测从公开名字及响应中的选项选择输入，不解密 token、不导入服务器答案。正常负载中的无效会话、重复猜测等业务错误应计为场景失败；错误路径可另设专门用例。

异常审计每题最多展示四张选项图片，终局四选一也会产生图片请求。题目和猜测推进后 token、请求体及响应体可能变大，因此应分别统计开局、中段和最后一轮。只连续调用 `/api/health` 或 `/api/new` 无法代表真实游玩。

## 第一轮怎么跑

以下为起始实验参数，不是已测出的服务器容量或正式验收承诺：

1. 单用户完成三个模式，确认请求序列、缓存模型和成功判断正确。
2. 预热后，依次尝试 5、10、20、50 个活跃虚拟用户，每档持续约 5 分钟；操作间加入 2–5 秒思考时间，后续按真实行为调整。
3. 每档都记录吞吐和延迟。达到错误率、延迟或内存上限就停止增压，无需把所有档位跑完。
4. 在仍满足体验要求的档位保持 30–60 分钟，观察内存是否持续增长、Swap 和错误是否累积。
5. 在中等负载下测试一次发布与回滚。把现有单服务重启造成的短暂中断记入报告，不把它当作零停机发布。

先分别跑纯 API 与 3 Mbps 静态混合负载，再讨论瓶颈。VU 表示按场景行动的虚拟用户，不等于每秒请求数，也不等于网页开着但没有操作的人数。若需要测固定到达率，使用 k6 的 arrival-rate 场景，并同时关注 `dropped_iterations`；不能因为服务变慢导致用户循环也变慢，就认为吞吐仍然稳定。参见 [k6 开放与封闭模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。

报告至少包含：

- 代码 SHA、数据版本、Ubuntu / Node / Nginx 版本、ECS 规格或宿主 CPU、内存 / Swap / 限速 / RTT 设置。
- 模式比例、用户数或到达率、思考时间、资源缓存模型、持续时间、压测器资源占用。
- 各 API 与各游戏阶段的 p50 / p95 / p99、实际完成请求数、业务及网络错误率、超时和丢弃的迭代。
- Nginx 出口吞吐、每局传输字节、首次可操作时间、图片完成时间。
- CPU、Node RSS、整机可用内存、Swap 活动、OOM / 服务重启、部署耗时和中断时间。

p95 表示 95% 的请求耗时不超过该值。可以先给 API 与首次加载分别设定体验目标，再通过 k6 thresholds 将违反目标的运行标记为失败；不要给较大的静态图片和 API 共用一个延迟阈值。参见 [k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)。

报告只保存聚合指标、错误类型及运行元数据，不记录完整游戏响应、token、谜底或生产密钥。

## 如何解释 3 Mbps 下的结果

3 Mbps 的理论总吞吐约为 375,000 字节/秒，即 366 KiB/秒，实际有效吞吐还受协议与网络影响。所有访客共享这条出口。

2026-09-08 的本地素材抽样中，`public/img/operators/final` 的 421 张图片中位数约 365 KiB。若某次访问确实需要四张接近这个体积且未缓存的图片，仅这些图片就需要约 4 秒的理想链路传输时间；这是带宽估算，不是实测页面耗时。实际页面还包括其他资源，不同模式可能使用更小的立绘，并不是每次进入都下载整个图片目录。

因此，“API 可以处理多少请求”和“多少人同时首次打开还能流畅游玩”会是两个不同的数字。若 API 延迟很低、CPU 尚有余量而出口已接近 3 Mbps，后续应优先评估图片体积、加载方式、缓存或对象存储 / CDN；若 API 本身先饱和，再定位应用逻辑与 CPU。

最后用同地域、同实例系列与规格、相同带宽 / 云盘 / 软件版本的测试 ECS 运行同一套场景。测量从外部客户端发起；记录实际网络条件后，才能把本地回归结果与真实生产规格的容量对应起来。
